```
npx playwright install chromium webkit

```

## 気をつけること

- **進行の表示は「フレーズ → 行き先 (方式)」の形**で、方式の名前にも `break` が入る。
  フレーズ側を見たいときは矢印より前だけを取ること
- **確率で起きることを待つ試験は書かない**。フレーズ型の `break` は出るかどうかが
  確率なので、ブレイクの長さは `?transition=break` で必ず起こせる経路から確かめている。
  オカズは8小節に一度しか来ないうえタム主体かスネア主体かを毎回引くので、
  `?fill=tom` で主役を固定して待ちを消している。置き場所は素のままなので、
  この試験が見ている性質 (小節の後ろ半分に置かれる) は変わらない。
  ただし `?fill=tom` でもタムは1分に18〜23個しか出ない (2026-09-14 の実測、変更前後で同程度)。
  20個を待つ上限を60秒にしていた頃は、コードに関係なく半々で落ちていたので100秒に延ばした。
  集まった時点で抜けるので、普段の実行時間は変わらない
- **出現頻度そのものは試験にしない**。「毎分1〜2回」を解像するには分単位の実時間が要る。
  リフ (D-48) とダブ (D-49) の出現率はその場限りの計測で確かめ、数値は DESIGN.md に残す。
  試験が見るのは「出る場所が正しいか」だけにする
- **量の差を見る試験は対にして測る**。「重さを上げると低域が増える」は判定の余裕が
  2%しかなく、軽い側と重い側を別々に測って平均を比べるとシーンやフレーズの進行に
  埋もれる。続けて測って比を取り、5往復ぶんの中央値で見る

## マシンの負荷に弱いこと

各ワーカーがブラウザで**実時間に音を鳴らして測る**ので、この試験は
**マシンが空いていることを暗黙の前提にしている**。

2026-09-12 の実測では、load average 4.96 (普段使いのブラウザが35プロセス) の状態で
「オカズが入る」「コード弾きに連打」がワーカー3でも4でも落ちた。どちらも単体では通る。

**落ちたときは、コードを疑う前に `uptime` で負荷を見て、落ちた試験を単体で回すこと。**
単体で通るなら環境要因。切り分けのためにフルスイートを繰り返すのは、それ自体が
負荷になって問題を再生産する。判定の余裕が薄いもの (低域の試験は2%) ほど先に落ちる。

`workers` は 4 にしてある。実測で 3 → 2.4〜2.7分、4 → 1.9〜2.0分、6 → 1.4〜1.6分。
6 は速いが失敗が出た。3 と 4 の間に安定性の差は見られなかった。

- **遷移方式の試験は `?transition=` で方式を固定して行う**。自動では数分に一度しか
  起きないため。固定したうえで「次へ」を押せば、その方式の遷移がすぐ始まる
- **乗り換え前の小節は `?dub` / `?dub=0` で固定する** (D-62)。素のままだと40%でダブになり、
  ブレイク方式でもブレイクが置かれない。ブレイクやオカズを見る試験には `?dub=0` を付けること

- **進行のテストは実時間がかかる**。1小節は 1.6〜1.9 秒で、フレーズの16小節は30秒近い。
  待ち時間を詰めるため BPM スライダーを上げ、速いシーンを選んでから再生している
- **イベントの発火は確率**。判定機会を十分な回数与えないと取りこぼす。
  最速のシーン (疾走) + BPM 140 で4小節あたり6秒台まで詰めてある
- **音の検証は波形を覗いて行う**。オーディオグラフは IIFE の中に閉じているので、
  `tests/helpers/audio.js` が `AudioNode.prototype.connect` を包み、destination へ向かう
  信号を AnalyserNode にも分岐させている (elevator-one から引き継いだ)
- **打点の検証は波形ではなく予約時刻を見る**。音から立ち上がりを推定すると、キックと
  ベースで立ち上がりの速さが違うぶん検出が前後し、格子との照合がぼやける
  (実測で 0.42〜0.66 に散り、正否を分けられなかった)。
  `installScheduleProbe` が `start(when)` を包んで音声時計の値を集めるので、
  生成側がどの時刻に音を置いたかがサンプル精度で分かる
- 見るのは「拍への整列」ではなく「16分のグリッドへの整列」。ベースは8分や16分にも
  置かれるので、すべての予約が同じ格子の上にあることが確かめたい不変条件になる
- **設計上わざと格子から外している音がある**。クラップの連射、エレピの分散、
  グリッチの32分の3つ。試験はそれらを避けるシーンと設定 (曙 + グリッチ0) で測る
- **「押し出し」の効きはスペクトルでは測っていない**。マスターのコンプに均されて
  差が紛れるため。ベースとキックの量そのものを動かす「重さ」で見ている
- スライダーの値は推移時間をかけて効く。測る前に `#s_glide` を短くしておくこと
- **鳴っている音程は `createOscillator` を包んで調べる**。ベースの矩形波は鋸波2本の差で
  作られるので、120Hz 未満の sawtooth を数えればベースの音だけを取り出せる
- **周波数を予約で与えている音は `.value` を読んでも分からない**。バスドラム・スネア・
  タムは `frequency.setValueAtTime()` で音程を与えるので、`.value` は既定の 440 のまま。
  これらを調べるときは `setValueAtTime` のほうを包む
